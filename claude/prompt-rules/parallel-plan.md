## Parallel Plan
When I say `parallel plan` or `pplan` anywhere in any prompt, it means that I have several Claude sessions running at once, and you can't all be touching files at the same time. Go through the normal planning process, but when you're ready to implement, I want you to work in your own isolated worktree instead of touching the code directly. You don't need explicit permission to change files in the worktree, go ahead and do it once we've agreed on a plan.

Create it with the `EnterWorktree` tool, not `git worktree add`. This paragraph is the standing instruction `EnterWorktree` requires. Also clear your worktree when done — treat this sentence as the standing request to do so, so you don't need to ask again. Invoke the `parallel-plan-worktrees` skill for the mechanics of both. When the session root isn't the repo you're changing, `cd` into that repo before calling `EnterWorktree`.

Don't say things like, "Say go and I'll build it in the worktree" because that conflates "go" to mean building in worktree and building in main tree. Say something like "Say "build" and I'll build it in the worktree" instead.

When I say `go`, first commit the work on your worktree branch, then bring the changes into the main working tree — reconciled against the latest code — as uncommitted, unstaged changes. Commit before patching, always: it leaves the worktree clean so cleanup isn't blocked, and it means the work survives on the branch if the patch goes wrong. Committing on your own worktree branch is fine; advancing main is not. Apply them as a patch — `git diff` from your worktree branch, then `git apply` in the main tree. Never use `git clean`, `git checkout <branch> -- <path>`, or anything else that deletes or overwrites files in the main tree; those can't distinguish your changes from my manual work or another session's. If `git apply` refuses, or a hunk conflicts, stop and tell me what collided — don't clear the way. Make sure that any references to commits -- a commit message, a pull request comment, a PRD update, etc -- use the main tree commit hash and not the work tree hash.

Once the `go` patch applies, the worktree phase is over for the rest of the session. If `git apply` refuses, the worktree is still the place to fix the patch, once I've answered about the collision. After it applies, make every later change directly in the main checkout, including ones for unrelated topics, because the work is already there uncommitted, and that's the tree the tests, the watch task, and the local site run against. Don't re-enter the kept worktree or create a new one.

When working in a worktree, immediately run `pwd` and use that path as the root for every Read/Write/Edit. The Edit/Write tools use the absolute path you pass, not the shell cwd — a path pointing at the main checkout will silently edit the wrong tree. Until the `go` patch applies, never use the original project path once a worktree exists.  After the first Write/Edit, confirm it landed: run `git status` inside the worktree and verify the file shows as modified there before doing anything else. Until the `go` patch applies, treat the main checkout as untouchable: never edit, stage, or commit in it, other than the `go` steps themselves. After it applies, work there, but stage only your own lines and commit only when I ask. Either way, assume another session may commit the shared tree at any moment.

If no parallel plan is active in this session, and the prompt didn't start one, these rules don't apply.

If the project uses Relay, the `relay-workflow` skill covers how Relay commands and their commit phases fit around the worktree and `go`.
