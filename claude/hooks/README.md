# Permission hooks

TL;DR: The Bash permission hooks and the `settings.json` rules depend on each other, so read this before changing either one, and restore the rules listed here if a hook is ever removed.

`claude/CLAUDE.md` keeps only the behavioral rules an agent needs in every session. This file holds how each hook decides, and which `settings.json` rules were removed to make it the sole authority. Agents find it through pointers in both `claude/CLAUDE.md` and the dotfiles repo's own `CLAUDE.md`, so keep both if it moves.


## Worktree auto-approvals
`hooks/file-command-permissions.py` auto-approves `git add`, `git commit`, `rm` of tracked files, and `cp`/`mv` that overwrite nothing untracked, inside a linked worktree under `.claude/worktrees/`, instead of prompting. A `git add` or `git commit` aimed at one with a single `-C <path>` counts too. It also auto-approves, from the main checkout or any worktree of the same repo, an `rm` of symlinks inside one of that repo's worktrees, tracked or not, outside their `.git` and `.claude`. Creating a link with `ln` always prompts, because the Edit tool writes through a directory link without one. Outside a worktree the hook leaves a commit that names its files to the auto-mode classifier, whose `soft_deny` rule passes it only when I asked for it, and it prompts on anything that might stage more than the files it names, because that sweeps in other sessions' work: an option off its safe list (`commit -a`, `--pathspec-from-file`, `add -A` with no pathspec), a glob or `:` pathspec, a directory, or a path at or above the repo root. It prompts on every `git push` (and `send-pack`, `http-push`, `subtree`), on any git global other than one `-C`, on a `-C` or a leading `command` ahead of a subcommand that `settings.json` gates by prefix (`clean`, `reset`, `rebase`, `tag`, and the like) unless the hook can vouch for the arguments itself, and on a subcommand that's a configured alias. It also auto-approves `git branch -D worktree-*` from the main checkout once that branch's content is already on HEAD, and read-only git subcommands (`diff`, `log`, `grep`, `fetch`, `show`, `status`, `ls-tree`, `symbolic-ref`, `stash list`, `stash show`, `worktree list`, and `remote get-url` -- the whole of `GIT_READ_ONLY_SUBCOMMANDS`) anywhere, with or without `-C <path>`, as long as no other global option sits ahead of the subcommand and no argument names a program to run or a file to write -- a `-c` or `--exec-path`, `grep -O`, `fetch --upload-pack`, a fetch from anything but a configured remote or with an option off the hook's allowlist, or an `--output` aimed anywhere but scratch prompts instead, and so does a `git diff` that would compare two files on disk rather than repository content -- `--no-index`, or two operands with either one outside the working tree, which git treats the same way even after a `--`. A `--no-index` diff still auto-approves when both operands are regular files inside the session's cwd, or are `/dev/null`, since the Read tool opens those without a prompt anyway. A `-C` doesn't widen that. A link to a file passes wherever it points, because git prints the link's text rather than its target. Anything else asks: git prints every file under a directory, follows a link to a directory to the file named like the other operand, and blocks reading a FIFO. A file that a `Read(...)` deny rule in the user's or the project's settings covers asks too, like `auth.json` or `.npmrc`. Outside any repository, a two-operand `git diff` asks, because every operand is then a file on disk, and so does `git grep`, along with `git grep --no-index`, `--untracked`, or `-f <file>` anywhere. Any git command prompts when its `-C` directory is one the shell rewrites first, like `~` or a glob, because every check is made against that directory. `git branch` and `git tag` auto-approve under the same global-option rule while they only list refs; a positional argument passes only after an option like `--list`, `-a`, or `--contains` has put git in listing mode, because `git branch -v foo` creates `foo`. `checkout`, `switch`, `branch`, `pull`, and `merge` go to the auto-mode classifier, whose `soft_deny` rule passes them only when I asked, in chat or through a skill I invoked; the hook still prompts on the forms that can destroy work or run a program, like `checkout -f`, a checkout operand that isn't a commit, `branch -f`/`-M`, or a pull from a URL. The hook judges each of those commands wherever it appears in the line and however it's spelled, and it only auto-approves the plain spelling of the program or a known absolute path to it, never `./git` or a copy somewhere else. A command nested inside a substitution, a compound command, or a `bash -c` string never gets an allow, and neither does one behind a wrapper other than `command`, since `env -C` or `sudo -D` would change the directory every check assumes. See Bash parsing below for how the line is read, and for the chain, `head`/`tail`/`wc`, and `/dev/null` rules.

That prompt was a safety net; where it's silenced, you carry its responsibility. The hook checks *containment*, not *intent* -- a silent approval means "inside the worktree and recoverable", never "correct". Before running one of these, confirm the operands are exactly what you intend and that you aren't deleting or overwriting work you didn't create. If the hook prompts or blocks a shape you expected to pass, that's information -- tell me; don't reword the command until it slips through.

Scratch cleanup under `.claude/tmp/` is scoped to the working directory's own `.claude/tmp/`, not any path containing those segments, so sweeping into another project's scratch still prompts. For `rm` and `cp`, a *relative* operand makes the hook stay silent, leaving the decision to settings.json's `rm .claude/tmp/*` and `cp * .claude/tmp/*` allow rules, while an *absolute* one is allowed by the hook itself -- those rules are literal prefixes that an absolute path can never match, so silence would drop the command to the auto-mode classifier with no guaranteed approval, and `running-commands.md` tells you to write absolute paths, so that is the spelling this actually arrives in.

`mv` into scratch is decided entirely by the hook, in both spellings, because `mv` deletes its source and the settings rules could not tell cleanup from displacement: they matched any source on the machine. The hook checks the sources instead, allowing one under an OS temp directory -- where the Chrome MCP must write a screenshot before you move it into the project -- or an untracked file inside the working directory. A tracked file or a file living anywhere else asks.

The hook and `settings.json` are interdependent, and removing either side alone opens a hole. A settings rule overrides the hook's decision, so making the hook the SOLE authority for a command meant deleting that command's rule: the `Bash(rm *)`, `Bash(git add *)`, `Bash(git commit *)`, and `Bash(mv *)` ask rules; a blanket `Bash(cp *)` allow rule; the ten `Bash(git -C * <subcommand> *)` allow rules, whose wildcard spanned tokens and so approved a `-c` or `--exec-path` smuggled in ahead of the subcommand; the bare `Bash(git diff *)`, `Bash(git fetch *)`, `Bash(git grep *)`, `Bash(git log *)`, and `Bash(git show *)` allow rules, which approved `grep -O<program>`, `fetch --upload-pack=<program>`, `fetch <path-or-ext::helper>`, and `--output=<file>`; the `Bash(git ls-tree *)`, `Bash(git remote get-url origin)`, `Bash(git status *)`, and `Bash(git symbolic-ref *)` allow rules, because they approved those commands without the hook ever seeing the line -- `git status --short | sed -n 1p` ran unprompted with its pipe unexamined, since nothing routed it to the operator guard; the `Bash(git stash *)` and `Bash(git stash list *)` allow rules, whose replacement is an ask rule for each of the eight stash subcommands that touch the working tree, since a blanket ask would beat the hook's allow and re-prompt `stash list` and `stash show`; the `Bash(mv * .claude/tmp/)` and `Bash(mv * .claude/tmp/*)` allow rules, which would otherwise let any file on the machine be moved into scratch unprompted; and the `Bash(git branch -D*)`, `Bash(git branch --delete --force*)`, `Bash(git branch -d -f*)` deny rules, whose replacement is `decide_branch_delete` proving the branch's content already exists on HEAD. The `Bash(git branch -v*)`-style listing allow rules went too, because a prefix can't tell `git branch -v` from `git branch -v -f main HEAD~1`; the hook approves listings by checking every argument instead. The `Bash(git checkout *)`, `Bash(git switch *)`, `Bash(git pull *)`, and `Bash(git merge --ff-only *)` ask rules went as well, because an ask rule overrides the classifier that now decides them. If the hook is ever removed or disabled, all of those commands match no rule at all and fall to the auto-mode classifier with no guaranteed prompt -- branch deletion most dangerously, because it went from denied outright to ungated. Any change that drops the hook must restore those ask and deny rules in the same edit. Flag this to me if you ever notice the hook missing while the rules are still absent.

The rules for deleting a branch are in `claude/CLAUDE.md`, because they apply in every session, not just when editing the hook.


## Command allowlist hooks
`hooks/command-allowlist-permissions.py` auto-approves specific subcommands of a CLI, forces a prompt for every other invocation of a covered command, and stays silent on lines that never run one, so `settings.json` applies to those normally. It also prompts when a covered name is handed as an argument to a program that might run it, like `parallel wp db reset` or `ssh host 'wp db reset'`, unless that program is on its `DATA_CONSUMERS` list of programs that only read their arguments. It covers WP-CLI (`wp`, including the Local.app absolute paths and the `mcp__local-wp__wp_cli` MCP tool), VIP-CLI (`vip`), and the Local CLI (`localwp`, whose `cli <site> -- <args>` reuses the WP-CLI allowlist, alongside `list` and `info`, while every other subcommand prompts), and the GitHub and GitLab CLIs (`gh` and `glab`) today, but nothing about it is specific to those five -- the `COMMANDS` table at the top of the file generalizes to any command, so covering a new one means adding an entry there rather than writing another hook.

The hook is the SOLE permission authority for every command in that table, because a `settings.json` `ask` rule beats a hook's `allow`. Making it authoritative for `vip` meant deleting the `Bash(vip *)` ask rule and the `Bash(vip wp post list *)` allow rule. Like every Bash hook, it runs on every line with no `if` filter. If the hook is ever removed or disabled, `vip` matches no rule at all and falls to the auto-mode classifier with no guaranteed prompt -- against production as readily as anywhere else. Any change that drops the hook must restore `Bash(vip *)` to the ask list in the same edit. The same goes for `localwp`, which has no settings rule of its own: restore `Bash(localwp *)` to the ask list too. Making it authoritative for `gh` and `glab` meant deleting their allow rules, because `Bash(glab mr *)` approved `glab mr merge`; restore `Bash(gh *)` and `Bash(glab *)` to the ask list if the hook goes. Flag it to me if you ever notice the hook missing while those rules are still absent.

The `wp db drop*`, `wp db reset*`, `wp eval*`, and `wp shell*` deny rules stay in `settings.json` deliberately, even though the hook would refuse them too. A settings `deny` beats a hook `allow`, so those are the one layer the hook cannot weaken, and they keep working if it's disabled.

Where the prompt is silenced you carry its responsibility. The hook checks the *shape* of a command, not its intent -- an allow means "this subcommand reads, or writes something recoverable, against an environment whose data is disposable", never "this is the right thing to run". For `vip` it additionally never auto-approves a production target, an unrecognized or missing environment, or a `--yes`/`-y` anywhere on the line. WP-CLI writes are on a separate local-only list: they auto-approve through `wp` and `localwp`, but through `vip` only reads do, so a write to staging or preprod always prompts. A few reads are local-only too, on `WP_LOCAL_READ_ALLOWED`: `user meta list` dumps every usermeta row at once, secrets included, so it prompts on VIP. `gh` and `glab` auto-approve only read subcommands like `pr view` and `mr list`, and only with flags on that subcommand's list in `GH_READ_ALLOWED` or `GLAB_READ_ALLOWED`, so `--web` and `--show-token` prompt. `-R`/`--repo` can sit anywhere, but only with a plain repository path, and a URL operand prompts, because a host there sends the request and that host's token elsewhere. Their `api` subcommand passes only as a GET to a REST path, with no `-F`, `--input`, `--hostname`, or header other than `Accept`, and `-f` only alongside `-X GET`. GraphQL always prompts, because it's sent as a POST whether or not it's a mutation. If the hook prompts for a command you expected to pass, that's information -- tell me; don't reword it until it slips through.

Three shapes are denied outright rather than prompted: a VIP target named any way other than a single `@org.env` token before the subcommand (the canonical format is in `running-commands.md`), an extra or misplaced `@` token, and a `wp`/`vip` binary at a path outside the hook's `BINARY_ALLOWED_PATHS`. A deny can't be approved at a prompt -- rewrite the command in the canonical form, or if the denied shape is genuinely needed, stop and tell me.

Most entries are prefix matches, but `db query` is validated instead, because the arguments after the subcommand are what decide whether it's safe. Read-only SQL auto-approves; a write, a second statement, an `INTO OUTFILE`, a `LOAD_FILE`, an `EXPLAIN ANALYZE`, or any flag off `WP_DB_QUERY_ALLOWED_FLAGS` prompts. That last one matters because WP-CLI hands assoc args it doesn't recognize straight to mysql, so `--execute=` would run a statement the validator never saw. On the Bash path, string literals are blanked out before that search, so `LIKE '%a;b%'` passes, and so does one `;` at the very end of the SQL. A SQL comment or a backslash prompts, because either can make the SQL run differently than it reads. The exception is `\%` or `\_` inside a string literal, which can't close the literal whether or not the server honors backslash escapes. That exception is for local sites only; on VIP any backslash prompts, because VIP-CLI's remote side parses the query again and may turn `\%` back into a wildcard. The `mcp__local-wp__wp_cli` path also searches the unstripped text, so any `;` or backslash still prompts there. A WP-CLI config with an `ssh:`, `http:`, or `inherit:` key anywhere, alias sections included, makes every `wp` and `localwp` command prompt, since it could point WP-CLI at a remote host. An unquoted glob in a WP-CLI assoc arg's value, like `--search=foo*`, doesn't prompt on its own, because bash can only expand it into more words with the same `--key=`; a glob anywhere else, or a brace or `$` expansion, still prompts.

`SHELL_FREE_TOOLS` is the one place the bash parser is skipped entirely. Local WP's `localwp-agent-tools` addon splits its `args` string itself and passes the array to Node's `execFile`, so no shell ever sees those arguments. Adding a tool to that set means verifying in the code that actually runs that it takes an argv and never a shell string; don't add one on the strength of a tool description.


## Bash parsing
Every Bash hook reads the command through `hooks/bash_ast.py`, which runs `shfmt --to-json` (Homebrew `shfmt`) and hands back every simple command the line can run. That includes commands inside `if`/`for`/`while`/`case`, subshells, groups, functions, `coproc`, `$(...)`, `<(...)`, backticks, unquoted heredocs, and literal strings given to `bash -c`, `sh -c`, `eval`, `env -S`, `watch`, and `sudo -s`. Quoting is resolved the way bash resolves it, the program name is compared as a lowercased basename because the filesystem is case-insensitive, `git-<sub>` exec-path binaries count as `git <sub>`, and wrappers like `command`, `env`, `exec`, `nohup`, `nice`, `sudo`, `timeout`, `chroot`, `xargs`, and `find -exec` are peeled off so the wrapped program is what gets judged. Hand-written quote scanners kept disagreeing with bash about heredocs, `$'...'`, comments, and nested commands, and each disagreement was a way past a gate; the parser removes that class of bug. Policy stays in the hooks.

Because the parser finds a command wherever it sits, none of the Bash hooks has an `if` filter in `settings.json`. A filter only matches the spellings it lists, so `"git" push`, `\git push`, `FOO=1 git push`, or `true && git push` would skip it. Every hook runs on every Bash line and stays silent on lines that don't concern it. If `shfmt` is missing, or a line won't parse, the hooks prompt rather than guess.

`dangerous-command-shapes.py` applies the rules that hold for every line, whatever the command:

- A line that chains more than one command -- `;`, `&&`, `||`, `|`, `&`, a newline, a compound command, or any of those inside a substitution or a `bash -c` string -- is **denied**, because the fix is always the same and always yours to make: send each command as its own tool call. A deny can't be approved at a prompt, so if a chained line is genuinely necessary, stop and tell me instead of rewording it.
- A command the hooks can't read prompts: a program name that expands at run time (`$EDITOR`), a non-literal `bash -c "$x"` or `eval "$x"`, a shell reading commands from stdin, or a wrapper option the parser doesn't know.
- Destructive git forms that `settings.json` denies are denied wherever they appear and however they're spelled, and `GIT_DIR`/`--git-dir` and the other repository-retargeting variables and options are denied.

A pipeline ending in `head`, `tail`, or `wc` isn't a chain, and is judged as the command feeding it, because those three read stdin, write stdout, and can do nothing else. Only a bare count or one of their own output-limiting flags is accepted after the name -- `tail -f` is excluded because it never exits -- and the tail can't rescue a command that wasn't allowed anyway: `wp db reset | head -1` still prompts on `db reset`.

A redirect whose target is `/dev/null` (`2>/dev/null`, `>>/dev/null`, `&>/dev/null`, `< /dev/null`) or a file descriptor (`2>&1`) doesn't count against a command, since it throws output away and can't write a real file. `> /tmp/x`, or a target that only looks like it (`/dev/null.bak`, `>&somefile`), still prompts when it's on a gated command.

`file-command-permissions.py` adds one more redirect exemption of its own, which the allowlist hook does not share: a `>` or `>>` writing into the working directory's own `.claude/tmp/`, or into Claude Code's own session directory under an OS temp directory, doesn't count against the command. The rest of `/tmp` and `/var/folders` is left out on purpose, because other programs keep files there. Containment resolves the whole path, final component included, so a symlink in scratch pointing outside it still prompts -- `> link` truncates what the link points at, which is the opposite of `rm link`. Every redirect on the line has to qualify or the line keeps all of them, and a destination holding a `$`, a backtick, a glob character, a backslash-newline, or a leading `~` never qualifies, nor does one that already has a second hard link. `git --output=<file>` is cleared by the same rule. For the same reason, `cp -l` and `cp -s` into scratch prompt.


## Keyword rules
`inject-keyword-rules.py` is a `UserPromptSubmit` hook. It adds a file from `claude/prompt-rules/` to the session's context when the prompt uses that file's keyword, such as "hold" or "pplan". Those rules are long and only matter in sessions that use the keyword, so keeping them out of `CLAUDE.md` saves space in every other session. `CLAUDE.md` keeps a short guardrail for each one, because compaction can summarize away the injected copy.
